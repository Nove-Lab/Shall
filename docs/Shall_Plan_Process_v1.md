# Shall — /plan Process (v1)

> The agent–human interaction flow that fills the plan plane — module designs, contracts and implementation tasks — on top of a specification a person has approved. Written in the graph's own relation names from the first line, so nothing here has to be translated before it is followed. Where this document and the code disagree, the code is right.

## Input

* Invocation form: `/plan <technical direction or change request>` — the user's input is passed as the command argument (the `$ARGUMENTS` slot in the agent template).
* `direction`: the user's natural-language statement of how the approved specification should be built, or of what about an existing plan should change. The user does not declare which; entry dispatch determines it.
* If the input is empty, do not start the process; ask for the direction first. Every phase below spends the user's attention, and a phase spent on a guessed direction costs more than one question.

## Entry Dispatch

1. Read the state of the whole project, band by band. Unapproved plan work comes first: anything yellow in the plan band is a phase somebody started and nobody agreed to, and it is finished or set aside before this request opens a new one.
   * Two nodes read as plan work although they are not filed in the plan band. An `Assumption` a `ModuleDesign` assumes is filed with the intent band, because `Assumption` is the one type the canon gives no layer of its own and that band is where such a node is drawn — it belongs to the phase that wrote it.
   * And one node is filed in the plan band without being plan work. A `Decision` lives in `plan/Decision/`, and no phase below writes one: a yellow `Decision` is somebody waiting on their own approval, not a phase left half-done. Leave it where it is, and do not offer to take it over.
   * A `SystemResponsibility` that is yellow **because it changed** — and that now carries an `IS_REALIZED_BY` relation — is this process's own unapproved work, not the specification's. A responsibility yellow because nobody has ever approved it belongs to `/specify`, and the two are told apart by which of the two reasons the read gives.
2. Check the upstream gate. The plan plane is written on top of an approved specification, and the check is local to the subgraph this direction touches rather than to the whole project.
   1. The shortcut: if nothing in the intent band is any color but green, the gate is passed and no walk is needed.
   2. The walk: for each `SystemResponsibility` this direction reaches, read its own color, then walk **up** — the `Scenario` that `DERIVES_RESPONSIBILITY` to it, the `UseCase` that `DETAILS` that scenario, the `Actor` that `PERFORMS` the use case, the `Goal` that is `PURSUED_BY` that actor, and any `Goal` that `REFINES` it — and **sideways** — the `Requirement`s the responsibility `REQUIRES`, each requirement's `AcceptanceCriterion` and `Constraint`, and the criteria the scenario carries. Every one of them must be green.
   3. If any of them is not, name those ids to the user, say which phase of `/specify` owns them, and stop. Do not plan over a specification a person has not agreed to: the plan would be rewritten by the judgment, and the work is thrown away.
   * This is the same set of nodes a task's readiness is computed over, which is why the gate is exactly this walk and not a wider one. A part of the project unrelated to this direction being unread cannot block planning, and must not.
3. Determine the mode. A responsibility in scope with no `IS_REALIZED_BY` relation out of it has no module yet → **new mode**: run everything from Phase 1. Otherwise → **revision mode**.
4. (Revision mode) Determine the highest layer the direction touches and set the entry phase.
   * Mapping: a module's boundary, what it is answerable for, or its internal design → Phase 1 / what a module publishes or calls, and the shape of the data that crosses a boundary → Phase 2 / what a piece of work is, what it waits on, or which criterion it aims at → Phase 3.
   * If the determination is ambiguous, settle it with the user through option-style questions — when in doubt, choose the higher layer. A boundary change re-cuts the contracts and the work below it; a change to one task never moves a boundary.
5. (Revision mode) Run from the entry phase downward, but scope the work to the **affected subtree**, not the whole plan.
   * Surgical change first: keep and revise the nodes that are there, additions are allowed, deletions only on the user's explicit request.
   * The approval set of each phase is limited to the nodes changed or added in that phase.
6. Phase 3 runs last in both modes. Phase 2 may pass on an empty set — a plan whose modules are all internal publishes no contract, and an empty set is owed no approval rite.

## 0. Common Rules (apply to every phase)

* **Question rule**: at most five questions per round, each offering 2–4 options plus a free-form answer. A question you could answer correctly yourself is not a question. The agent-side interface that carries these questions binds them tighter still — four to a round — so a round is written to the smaller number and never split to evade it.
* **Default rule**: an ambiguity a reasonable default can carry is not asked about — it is recorded as an `Assumption` and anchored with `ASSUMES` from the node that assumes it. In this plane **only a `ModuleDesign` may assume**: a contract's or a task's default is hung on the module that owns it, and a default with no module to own it is asked about instead, because the alternative is an orphan.
* **Full-resolution rule**: an ambiguity or conflict no default can carry is resolved by questions inside the phase — a phase cannot close over an open point. If the user defers, narrow the scope until a decision can be made together, and ask again.
* **Dual-approval rule**: every phase closes with two-stage approval — (1) explain the whole set of outputs in the terminal and get a yes, (2) write the files, run the check until it passes, then tell the person that approval cards are waiting and wait for the browser judgment. Confirm afterwards that every id this phase wrote or changed reads green.
  * A rejection is a work order, given whole. Nodes converge by revision and never by deletion: the moment a file's content changes, the rejection lapses of its own accord and the node is waiting to be read again.
  * Do not open the next phase before every card of this one is green.
* **Fix Spec first**: at the start of every phase, and every time work resumes after waiting on a judgment, read what the board says is red and clear it before writing anything new. New nodes on top of a red graph bury the red and hand the person a card they cannot judge.
* **Level rule**: this plane is written at the level of modules, components and contracts. Classes, functions, file layouts and paths are **not written here** — they are what the work turns up while it is being done, and a plan that names them is a plan that will be wrong before the first turn of work ends. One exception, and it is the user's to make: if the direction explicitly asks for paths, confirm it once in Phase 3, record them in the task's own body, and say in the terminal explanation that the level rule was relaxed on request.
* **Convention Survey**: before Phase 1's decomposition begins, read the project's own documents — its readme, a contributing guide, anything under a docs folder, a design record, the rules file the project loads into every session — and collect the conventions and principles that bear on this plan. Sort what you find three ways:
  * (a) A norm that genuinely **binds** requirements or design is promoted to a `Constraint` in the specification. It is not left as a reference to an outside document: an outside document can be revised without anything in the graph turning a color, so a plan grounded in one is grounded in an untracked dependency. The promotion is a round-trip through `/specify` in revision mode, done in the same session and returned from.
  * (b) A **design convention** — a habit of arrangement, a naming practice, a layering the project already keeps — is followed, and the node whose design followed it says so in its own body, naming the path of the document it came from.
  * (c) A **conflict** between the user's direction and an existing convention is never settled silently in either direction. Put it to the user as an option question and let them judge.
  * If the project has no such documents at all, say so once, ask once whether there is an unwritten convention worth honoring, and go on.
* **Grounds duty**: where an outside document or a piece of investigation actually made a design decision, the terminal explanation of that phase must say **which decision followed which grounds**, naming the source. The record in a node's body is for tracing it back afterwards; this duty is for the moment of approval, so that nobody approves a decision without having seen what produced it.
* **Gaps in the specification are the normal path.** Planning is where a missing responsibility, an unjudgeable criterion or a term pulling two ways is discovered — that is what happens when a specification is read closely enough to build from, and it is not a failure of either document. The return path is `/specify` in revision mode: take the gap there, let it be approved, and resume at the step this phase left.
* **No stored backlog**: every task belongs to a module, and nothing is planned that the specification does not ask for. There is no closing phase collecting cross-cutting work, no list of chores parked for later, and no task standing on its own. The place for a verification scenario is an acceptance criterion in the specification; the place for an end-to-end proof is the evidence the execution plane records.
* **Approval principle**: a change to an approved node is a revision of that node's file, not a second node saying the newer thing.
* **Three words this document does not use.** It does not say the plan is *registered* in a database — the plan is files, and writing one is the whole of putting it there. It does not say a type has *fields* — a node's body is free markdown, and the starting file the tooling writes is the only place that suggests a shape for it. And it never says "the card": a phase arrives in the queue as one or more cards, and a person told to look for one stops after the first.

## 1. Module Design Phase Process

The phase runs in two stages inside one approval. Steps 1–10 decompose, in the conversation, with nothing written to disk; step 10 is a terminal checkpoint of the decomposition alone. Steps 11–13 design, and step 13 is the one place this phase writes files. A module reaches the queue once, complete, rather than twice.

1. Run the **Convention Survey** and sort what it finds three ways (Common Rules). Finish the promotion round-trip for anything in (a) before the decomposition leans on it.
2. **Collect the drivers.** Take every green `SystemResponsibility` in scope, and add to them the non-functional `Requirement`s and the `Constraint`s that bind them. A structure cut from functional responsibilities alone splits again the first time a quality requirement is put to it.
   * The drivers are read and not recorded as relations: the canon draws no relation between a `ModuleDesign` and a `Requirement` or a `Constraint`. That is why the grounds duty exists — the reasoning that used a driver leaves no trace in the graph unless the design says so in its own words.
3. **Decompose from responsibility to structure, never the other way.** Start from the set of responsibilities and assign them to modules. Drawing a structure first and fitting responsibilities into it is forbidden: it produces a plan that answers to the drawing rather than to the specification.
4. **Ask of each candidate module: what design decision does this module hide?** A module is the unit that wraps one decision likely to change — how something is stored, which outside system is spoken to, which algorithm is used — and the answer is written in the module's own body as a required part of its description.
   * The shape of the decomposition is free — stages, layers, a store and its users, whatever the drivers call for — but an answer that only names the module's position in the flow has not named a decision yet. Ask what would change inside it that the rest must never see, and if nothing answers, go back to step 3.
5. **Verify each assignment with two questions.** (a) Do the responsibilities assigned to one module **change for the same reason**? If not, that is a signal to split. (b) Does every dependency between modules run through a contract? A dependency that reaches past a contract into another module's internals is not allowed.
   * The contracts themselves are Phase 2's output. Here you only **mark the hand-over points** where one module asks something of another; those marks are the material Phase 2 harvests.
6. **Settle assignment conflicts by information.** A responsibility is seated in the module that holds the information needed to carry it out.
7. **A purely technical module is legitimate.** A storage adapter, a transport layer, a module that exists to hide a mechanism corresponds to no concept in the domain, and it is not required to. Do not force a domain correspondence on every module.
8. **If one `Term` is asked to mean different things in different modules, stop.** That is either a term that must be split or a boundary that must be reconsidered. Take the split to `/specify` in revision mode, or re-cut the boundary — and let the user settle which.
9. **Self-check the decomposition**: every key responsibility in scope reaches at least one module ∧ no module hangs off no responsibility ∧ no cycle among module dependencies ∧ nothing violates a constraint.
10. **Get terminal approval of the decomposition** — the module list, each module's boundary, what is assigned to it and what it hides — before spending anything on design. Nothing is written to disk at this checkpoint; a boundary error caught here costs a conversation, and caught after the design costs the design.
    * If it is not approved, take the objection back to step 3 and repeat the decomposition.
11. **Design each module, in four parts.** Structure and behavior are not invented on a blank screen: they are derived from the approved scenarios and responsibilities, the same way the specification's own layers were derived from the layer above.
    1. **Role** — one sentence naming the single charge this module answers for. If the sentence cannot be written without "and", two roles are mixed: return to step 3 and consider splitting. Six role kinds help start the sentence — a keeper of information, a provider of a service, a coordinator, a controller of flow, a connector to something outside, an organiser of structure — and they are a starting point for the wording, never a classification to be enforced.
    2. **Structural design** — the module's internal organization, described as a **named arrangement and its departures** rather than invented shapelessly. Name the arrangement it follows — layered, a pipeline of stages, a mediated set of parts, a store at the center with its users around it — say why that one, and say where this module departs from it. The level stays at components: no classes, no functions, no files.
    3. **Behavioral design** — **walk the scenarios through**. For each key scenario this module takes part in, follow the steps: who acts at each one, what is asked of whom, what is handed back. **Mark every hand-over between modules** — those marks are what Phase 2 harvests as contract obligations. A module that holds state adds a statement of that state: what states there are, what moves between them, and what triggers each move — at the level of the specification, never of code.
    4. **Rationale** — for every structural or behavioral choice that is not self-evident, three things: what was decided, what alternatives were weighed, and which driver settled it — a non-functional requirement, a constraint, or a convention the survey found. This is where the survey's source paths and the grounds duty land.
12. **Verify the design against the assignment.** Every responsibility that a module is `IS_REALIZED_BY` must appear in at least one behavioral walkthrough — a responsibility absent from every walkthrough is one the design has not yet absorbed. If a walkthrough contradicts the decomposition — a flow that reaches past a module, an actor other than the one the assignment named — fix the design, or return to step 3 if the boundary is what is wrong.
13. Perform dual approval on the whole set (terminal explanation → write the files and check → cards in the queue → confirm the colors).
    * The anchoring relation is `SystemResponsibility —IS_REALIZED_BY→ ModuleDesign`, written in the **responsibility's** file, so every responsibility that gains a module is read again. That is the graph asking whether the responsibility still says the right thing now that something hangs off it.
    * If terminal approval is not given, return by the layer of the objection: a boundary or an assignment → step 3, one of the four design parts → step 11.
    * Approval gate: step 9's four conditions ∧ every module carries all four design parts ∧ every responsibility a module realizes appears in ≥1 walkthrough ∧ no walkthrough contradicts the decomposition.
    * Upon web approval, proceed to Phase 2.

## 2. Contract Phase Process

1. **Harvest the contracts from the walkthroughs.** Every hand-over marked in Phase 1's behavioral design is the origin of an `Interface` obligation, and every piece of data that crosses a boundary is a candidate `DataSchema`. A contract item with no walkthrough behind it has to justify itself: ask what asked for it, and if the answer is "it seemed useful", it is not a contract.
2. **An `Interface` describes the distribution of obligations, not a list of signatures.** Three parts carry it: what the caller must guarantee before calling, what the module guarantees when it returns, and what holds true before and after every call whatever else happens.
3. **Name the consumer of every published item.** The minimum-disclosure rule: an interface is what its consumers need, not everything that is left over after the hiding. The walkthroughs already say who consumes what. An item whose consumer cannot be named is over-exposure — consider removing it. A module with no outside surface publishes no interface at all, and that is a complete answer.
4. **Let the form follow the kind of module.** A service is described as endpoint obligations, a command-line tool as its commands and their argument shapes, a library as its public function contracts, a reader of input as the grammar it accepts. Describe in the form that fits, and stop at the contract: implementation code is not written here.
5. **Derive each `DataSchema` with three questions**, rather than copying a `DomainEntity` one-for-one: does this need an identity, or is it compared whole as a value, or is it a bundle that must stay consistent together — and a bundle is one schema unit. A schema names the concept it comes from with `REPRESENTS`.
6. **Carry the requirements' validation rules into the schema.** Format, range and presence rules the specification already states are the schema's constraints; do not restate them in new words and do not invent ones the specification does not ask for.
7. **Reconcile the contracts against each other** before the phase closes. The same data defined two ways by two schemas is a contradiction that will be discovered by whoever implements the second one.
8. Perform dual approval on the whole set (terminal explanation → write the files and check → cards in the queue → confirm the colors).
    * `ModuleDesign —EXPOSES→ Interface` and `ModuleDesign —CONSUMES→ Interface` are written in the **module's** file, and `Interface —CARRIES→ DataSchema` in the interface's; so each module that gained a contract line is read again.
    * If terminal approval is not given, return by the layer of the objection: the obligations → step 2, what is exposed → step 3, the schemas → step 5.
    * Approval gate: every module with an outside surface has ≥1 interface ∧ every hand-over marked in Phase 1 is absorbed by some contract ∧ every schema names the concept it represents ∧ no contradiction between contracts.
    * If every module in scope is internal, this phase writes nothing, holds no approval rite, and produces no schema either — a schema is held to the graph by the interface that carries it, so a schema with no interface would be an orphan.
    * Upon web approval, proceed to Phase 3.

## 3. Task Decomposition Phase Process

1. **Cover in both directions.** Every `ModuleDesign` in scope is decomposed into at least one `ImplementationTask`, and every task belongs to at least one module. A task belonging to no module is not created for any reason.
2. **Before allowing a task to span modules, ask what it really spans.** If what the work has in common is not a task but a **structure** — a shared bus, the build and tooling, a common scaffolding every module sits on — that is a missing module: a purely technical `ModuleDesign` whose hidden decision is exactly that structure. Return to Phase 1, erect it, and hang the work off it as a single parent. A task that appears to span nearly every module is **always** this signal.
3. **A task that genuinely spans modules takes all of them as parents.** Integration work and the wiring between modules are allocated by every `ModuleDesign` they concern, and not by one chosen arbitrarily. Readiness is computed over the union of every parent's upward chain, so a spanning task cannot be started before all the specifications it touches are agreed — the order takes care of itself.
4. **Four quality tests on every task.**
   * **Independent** — as few dependencies between tasks as the work allows. Necessary ones are written as `DEPENDS_ON`, and there is no cycle.
   * **Method-free** — it says what is finished when it is done, never how to do it and never which files it touches. Paths are what the work turns up (Common Rules, level rule); the one exception is the user's explicit request, confirmed once here and said out loud in the terminal explanation.
   * **Traceable** — a task `TARGETS` **zero or one** criterion. Never two.
   * **Sized** — finishable in one turn of work. Larger than that, split it; smaller than that, do not, because chopping finer only lengthens the chain of things waiting on each other.
5. **Store no order and no labels.** Write only the precedences, as `DEPENDS_ON`; what can be started and what can run in parallel is computed from them. Do not invent classifications like "foundation work" — a task many others wait on stands first in the graph without being told to.
6. **Cover the criteria.** The cardinality is one direction 0..1 and the other 1..N: a task aims at one criterion at most, and one criterion may be shared out among several tasks. **By the close of this phase every `AcceptanceCriterion` in the plan's scope — scenario-attached and requirement-attached alike — must be targeted by at least one task.** An untargeted criterion means the plan is not finished: derive the task that will close it, and let the walkthroughs say which module it belongs to.
    * A task that targets no criterion is allowed — preparation, internal tidying — but its completion cannot be read off a criterion being closed. It is finished when a person closes it over the completion reports claiming it, and nothing else; evidence cannot be filed under it, because evidence is shown against a criterion and this task aims at none.
7. Perform dual approval on the whole set (terminal explanation → write the files and check → cards in the queue → confirm the colors).
    * `ModuleDesign —ALLOCATES→ ImplementationTask` is written in the **module's** file; `DEPENDS_ON` and `TARGETS` are written in the **task's own** file, so that planning work never touches a criterion's file and never moves somebody's settled judgment.
    * If terminal approval is not given, return by the layer of the objection: which module a task belongs to → step 1, a task that spans → step 2, the quality tests → step 4, the coverage → step 6.
    * Approval gate: coverage in both directions ∧ no cycle among `DEPENDS_ON` ∧ no task targeting more than one criterion ∧ no untargeted criterion in scope ∧ after approval, at least one task shows on the board as ready to start.
    * If the board is empty after approval, the first quality test was broken somewhere: something every task waits on has not been agreed, or the tasks wait on each other in a chain with no beginning.
8. Declare the plan complete: tell the person the plan plane holds together, name the tasks the board says can be started, and finish. Changes to the plan after this come back through `/plan <change request>`, which enters in revision mode and runs only the affected layer and below, scoped.
