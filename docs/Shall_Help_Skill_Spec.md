# Shall — help 스킬 구현 명세

`/shall.help` — Shall 자체에 대한 물음표("이게 뭐지", "나 뭐 해야 하지")에 답하는 인도자 커맨드를 구현한다.
work·raise 스킬과 별도 작업이다 — 진행 중인 해당 구현을 건드리지 않는다.

## 0. 정체

- 사용자 상태별 문 가운데 마지막 빈칸을 메운다: /specify·/plan(만들 것을 아는 사람) / work(일 시키는 사람) / raise(**프로젝트**에 대한 물음표) / **help(Shall과 자기 할 일에 대한 물음표)**.
- raise와의 경계: raise의 물음표는 프로젝트를 향하고("결제 쪽 이상한데"), help의 물음표는 Shall과 사용자 자신을 향한다("이 도구 뭐지", "다음에 뭐 하지"). 사용자가 help에 프로젝트 물음표를 가져오면 raise를 안내한다 — 대신 답하지 않는다.
- CLI `shall help`(기계용 명령 레퍼런스)와 이름이 같은 것은 의도다 — 같은 질문의 사람용 표면. 안내문에 이 관계를 한 줄로 언급한다.

## 1. 출력 구성 — 3부

### 1부. Shall 소개 + 사용법 (정적)

- Shall이 무엇인지 (스펙 그래프 · 사람의 승인 · 에이전트의 작업 사이클 — 서너 문장), 커맨드 지도 (/specify · /plan · /shall.work[.todo|.report, --auto|--dry] · /shall.raise · /shall.help — 각 한 줄), 색·마크의 뜻 (R/Y/G, open/closed — 각 한 줄).
- 이 부분은 프로젝트 상태와 무관하게 고정이다. 스킬 본문에 직접 담는다 (이 스킬의 내용물 자체가 안내문이므로 — "얇은 스킬" 원칙의 정당한 예외).
- 장황 금지 — 전체가 화면 하나에 들어오는 분량.

### 2부. 이 프로젝트의 간략한 상태 (계산)

- `shall status --json`·`shall board --json`을 읽어 요약: 게이트/단계 진행, red·yellow 개수, open/closed AC 규모, 보드 요약 (Fix Spec n / Ready m), 미응답 blocking Finding 유무.
- 숫자 나열이 아니라 문장으로 — "스펙은 승인 대기 3건, 구현 가능한 작업 2건이 있습니다" 수준.

### 3부. 다음 권장 행동 (1×2의 합성 — 이 스킬의 존재 이유)

상태를 읽어 "지금 이 커맨드를 치면 됩니다"로 번역한다. 결정 트리 (위에서부터 첫 일치):

| 상태 | 권장 |
|---|---|
| `.shall/` 없음 (비프로젝트) | 1부 소개 + "`shall init`으로 이 폴더를 Shall 프로젝트로 만드세요" — 2·3부는 생략 |
| 스펙 공백 (인텐트 노드 없음) | "`/specify`로 시작하세요 — 무엇을 만들지부터" |
| red 존재 | "고칠 것이 있습니다 — `/shall.work`가 Fix Spec부터 잡습니다" (반려 red면 rationale 존재 언급) |
| yellow 적체 (리뷰 대기) | "웹 리뷰 큐에 승인 대기 n건 — 승인이 진행의 선행 조건입니다" |
| Ready task 존재 | "`/shall.work`로 구현을 돌리세요 — 처음이면 `--dry`로 예보부터 볼 수 있습니다" |
| 미응답 blocking Finding만 남음 | "답을 기다리는 발견이 있습니다 — 웹에서 확인해 주세요" |
| 전부 green·closed, 보드 공백 | "이 단계는 완주했습니다 — 다음 의도가 있으면 `/specify`로" |

- 복수 상태가 겹치면 최대 2개까지 권장 (우선순위 순). 셋 이상 나열하지 않는다 — 인도자는 갈림길을 줄여주는 존재다.

## 2. 규율

- **읽기 전용 — 절대 실행하지 않는다.** 권장은 커맨드 안내까지다. "제가 지금 할까요?"로 넘어가지 않는다 — 인도자는 문을 가리키지, 문을 대신 열지 않는다.
- 어떤 파일도 쓰지 않는다. Shall에 아무것도 등록하지 않는다.
- 비프로젝트 폴더에서도 동작한다 — help는 프로젝트 밖에서 살 수 있는 유일한 스킬이다 (첫 만남이 대개 그 상황이다).
- 인자는 선택이다: `/shall.help <질문>` 이면 3부를 그 질문 중심으로 답하고, 없으면 3부 전체 구성으로.

## 3. 완료 기준

- 비프로젝트 폴더: 소개 + init 안내만 출력, 오류 없음.
- 프로젝트 폴더: 3부 구성이 화면 하나 분량으로 출력되고, 권장이 결정 트리와 일치한다.
- 실행 전후 어떤 파일 변화도 없다 (쓰기 0).
- 프로젝트 물음표("X가 이상한데")를 받으면 raise 안내로 응답하고 직접 탐색하지 않는다.

## 4. 구현 결정 (2026-08-23)

구현하며 확정한 것. 명세 본문은 고치지 않는다.

1. **blocking Finding 관련은 2부·3부에서 전부 뺀다.** `shall status --json`은 Finding의 `blocking` 마크를 싣지 않고, 홀로 선 Finding은 yellow 노드로 큐에 오르므로 "yellow 적체" 행이 그 경우를 덮는다. help는 Finding 파일을 열지 않는다.
2. **2부의 계산 범위는 status·board의 필드뿐.** 밴드별 노드 수(`band`), 색 수(`color`), 반려 수(`rejection`), criterion의 open/closed(`closure`), task 상태(`taskState`), 보드 양쪽 길이, `broken`·`missing`. 카드 수는 없으므로 "yellow 노드 n개"로 말하고, 게이트·단계 필드는 없으므로 밴드별로 말한다. 색·준비·닫힘을 스스로 판정하지 않는다.
3. **철자는 플러그인 네임스페이스대로 `/shall:help`**(명세의 `/shall.help`·`/shall.work`는 같은 것). 구현은 `plugin/commands/help.md`(문 — 멈추지 않는 게이트, 질문의 주인 가리기, 인계)와 `plugin/skills/shall-help/SKILL.md`(1부 정적 본문을 스킬 본문에 직접 — §1의 예외 그대로). CLI `shall help`와의 관계는 1부 명령 표의 한 줄.
4. **결정 트리에 두 행을 보탠다** — first-match 표의 구멍을 막기 위해: "전부 green이고 Plan 밴드 노드 없음 → `/shall:plan`", 그리고 나머지(green·열린 criterion·빈 보드) → "브라우저에서 판정할 것이 남음". 권장은 최대 2개 그대로.
5. **help는 feed에 기록하지 않는다** — 인도는 활동이 아니다. 쓰기 0, 권장 명령·`shall init`·`shall`(인자 없음) 실행 0, 읽는 것은 `shall status --json`·`shall board --json` 두 답뿐. 프로젝트 물음표는 `/shall:raise <그 말 그대로>`로 보내고 답하지 않는다.
