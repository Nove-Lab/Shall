# 작업 지시 — Shall `/plan` 프로세스 설계 + 플러그인 증분 구현 (1차)

## 목표

plan 플레인(ModuleDesign · Interface · DataSchema · ImplementationTask)을 세우는 `/shall:plan`을 만든다. 두 단계로: (1) 프로세스 정본 문서를 작성해 `docs/`에 커밋, (2) 기존 specify 플러그인 패키지에 plan 증분을 구현하고 실전 테스트한다.

## 표기 금지 규칙 (모든 산출물에 적용 — 최우선)

* 산출물(프로세스 문서·스킬·커맨드·템플릿·에러 메시지)에 **경쟁 도구 이름(Spec Kit 등)을 언급하지 않는다.** 조사·비교는 작업 과정에서 자유이나, 결과물은 Shall 고유 프로세스로만 서술한다.
* 산출물에 **이론·논문·인명·방법론 고유명사를 쓰지 않는다.** 아래 "설계 지침"은 이미 행동 규칙으로 풀어놓은 것이니 그대로 Shall의 규칙으로 서술한다 — 독자(에이전트)가 무언가를 검색해야 이해되는 서술은 실패다.

## 기반 확인 (작업 시작 시 최신 원천을 직접 확인할 것)

1. **specify 구현 현재 상태**: 플러그인 구조·shall-authoring 스킬·커맨드/스킬 분담·이중 승인의 구현 번역 방식. plan은 같은 문법의 증분이다 — specify와 다른 구조를 발명하지 않는다.
2. **데몬 현재 동작**: 색 판정·Review Queue 번들·Task Board(Fix Spec/Implement, Ready 계산, Done 정의)·CLI(status/board/check/add-spec-node)의 실제 동작. Task Board가 소비하는 task 구조(ModuleDesign의 자식, depends on, 대상 AC)의 현재 스키마 표현을 확인하고 그에 맞춘다.
3. **프로세스 정본**: `docs/`의 specify 프로세스 최신 버전 — 공통 규약(질문·기본값·전량 해소·이중 승인)과 진입 디스패치 문법을 plan 문서가 그대로 상속한다.
4. **Claude Code 형식**: 플러그인·커맨드·스킬·훅 명세 최신 확인.
5. (선택) 경쟁 도구의 계획 단계 재조사 — 작업 참고용으로만. 산출물 표기 금지 규칙 적용.

## 프로세스 골격 (확정)

3 phase다: **Module Design → Contracts → Task Decomposition.** ModuleDesign 노드는 모듈의 정의(경계·할당)와 설계 — 역할 서술(role), 구조 설계(structural), 행위 설계(behavioral), 그리고 그 근거(rationale) — 를 함께 담으며, Phase 1이 분해와 설계를 한 phase 안의 두 단계로 수행한다(분해 후 터미널 중간 승인, 설계까지 마친 뒤 등록·웹 승인 1회 — 같은 노드가 웹 승인대에 두 번 오르지 않는다). 마무리 phase(횡단 작업 모음, 실행 가이드 문서 등)는 두지 않는다 — 검증 시나리오의 자리는 스펙의 AC가, end-to-end 증명은 실행 플레인의 Evidence가 이미 갖고 있고, 스펙에 근거 없는 횡단 작업을 태스크로만 세우는 것은 금지된 저장 백로그다.

* 입력: `/shall:plan <기술 방향 또는 수정 요구>` — `$ARGUMENTS` 관례, 빈 입력 처리 동일.
* 진입 디스패치: specify와 동형(신규/수정 모드, 수정 모드는 영향 서브트리 국한·surgical 우선). 대응표: 모듈 경계·할당·설계 변경 → Phase 1 / 계약 변경 → Phase 2 / 태스크 변경 → Phase 3. 모호하면 상위 층.
* 진입 게이트(서브그래프 국소): 계획 대상 서브트리의 상류(SR와 그 상위 사슬, 형제 REQ·AC·Constraint)가 all-green. 프로젝트 전체 loop-ready는 요구하지 않는다. 미충족 시 /shall:specify로 안내.
* phase마다 정제 루프(선택지형 질문 ≤5·2~4 선택지, 기본값→Assumption, 전량 해소)와 이중 승인(터미널 설명 → spec/ 저작+check 통과 → 웹 번들 승인 → status 확인)을 specify와 동일하게 적용.
* **기존 규약 조사(Convention Survey)** — Phase 1 시작 전 공통 규율: 프로젝트의 기존 문서(README, CONTRIBUTING, docs/, 설계 기록, CLAUDE.md 등)에서 계획 관련 규약·원칙을 수집해 3분기 처리한다. (a) 요구·설계를 실제로 구속하는 규범은 Constraint로 승격한다(외부 문서는 개정돼도 stale 연쇄가 돌지 않는 미추적 의존이므로 참조로만 남기는 것은 불허 — 승격 경로는 /shall:specify 수정 모드 왕복, 같은 세션에서 이어서 수행). (b) 설계 관례는 준수하고 이를 따른 노드 description에 출처 경로를 명기한다. (c) 사용자의 기술 방향과 기존 규약이 충돌하면 조용히 어느 쪽도 이기게 하지 않고 선택지형 질문으로 사용자가 판정한다.
* **근거 설명 의무**: 외부 문서·조사가 설계 결정에 사용됐다면 해당 phase의 터미널 승인 설명에 "어떤 결정이 어떤 근거(출처 포함)를 따랐는지"를 반드시 포함한다. description의 출처 기록은 사후 역추적용, 이 의무는 승인 순간용 — 사람이 근거를 못 본 채 승인하는 일이 없게 한다.
* plan 중 스펙의 공백·오류 발견(누락 SR, 판정 불가 AC 등)은 실패가 아니라 **정상 경로**로 서술한다 — 스펙과 계획은 교대로 정밀해지는 관계이며, 복귀 경로는 /shall:specify 수정 모드다.

## 설계 지침 — phase별 행동 규칙 (프로세스 문서의 스텝은 여기서 도출한다)

### Phase 1 — Module Design (전반부: 분해)

* 시작 스텝은 드라이버 수집이다: 대상 서브트리의 green SR 전부에 **비기능 REQ와 Constraint를 더해** 분해의 입력으로 삼는다. 기능 책임만 보고 나눈 구조는 품질 요구 앞에서 다시 갈라진다.
* 분해의 방향은 항상 책임→구조다: SR 집합에서 출발해 모듈에 할당한다. 구조를 먼저 그리고 책임을 끼워 맞추는 역방향을 금지한다.
* 모듈 경계의 판별 질문: **"이 모듈이 숨기는 설계 결정은 무엇인가."** 모듈은 바뀔 가능성이 높은 결정(저장 방식, 외부 연동, 알고리즘 선택 등)을 하나씩 감싸는 단위이며, 이 답을 ModuleDesign description의 필수 서술 항목으로 강제한다. 답이 "처리 순서상 이 단계라서"라면 잘못된 분해다 — 입력→처리→출력식 흐름 분해는 재분해 신호.
* 할당 검증 두 질문: (a) 한 모듈에 할당된 SR들이 **같은 이유로 함께 바뀌는가** — 아니라면 분리 신호. (b) 모듈 간 의존이 계약(Phase 2 산출물) 경유로만 성립하는가 — 내부 구조를 건너 짚는 의존은 금지.
* 할당 갈등의 판정 규칙: 책임은 그것을 수행하는 데 필요한 정보를 가진 모듈에 앉힌다. 어느 도메인 개념에도 대응하지 않는 순수 기술 모듈(저장 어댑터, 전송 계층 등)은 정당하다 — 모든 모듈에 도메인 대응을 요구하지 않는다.
* 같은 Term이 모듈에 따라 다른 정의를 요구받는 상황이 발견되면 그대로 진행하지 않는다 — Term 분리(/shall:specify 수정 모드) 또는 모듈 경계 재고의 신호로 다루고 사용자와 확정한다.
* 서술 수준: 모듈·컴포넌트 수준까지만. 클래스·함수·파일 구조는 금지(실행의 발견 사항).
* 분해 판정 기준(중간 승인 전 자기 점검): 대상 서브트리의 핵심 SR 전부가 ≥1 ModuleDesign에 도달 ∧ 고아 ModuleDesign 없음 ∧ 모듈 간 의존 무사이클 ∧ Constraint 위반 없음.

**분해 중간 승인(터미널)**: 분해 결과(모듈 목록·경계·할당·숨기는 결정)를 사용자에게 설명하고 터미널 승인을 받은 뒤에 설계로 넘어간다 — 경계 오류를 설계 투자 전에 차단하는 체크포인트. 이 시점에는 파일을 등록하지 않는다(등록·웹 승인은 phase 종료 시 1회). 미승인 시 분해 스텝을 반복한다.

### Phase 1 — Module Design (후반부: 설계)

각 ModuleDesign의 설계 4항(role / structural / behavioral / rationale)을 채운다. 설계 수확의 원리는 specify와 같다: 구조와 행위는 빈 화면에서 발명하지 않고 **승인된 시나리오와 SR에서 도출**한다.

* **역할(role)**: 모듈의 소임을 한 문장으로 — "이 모듈은 무엇을 맡는 자인가". "그리고(and)" 없이 쓸 수 없으면 역할이 둘 섞인 신호이므로 분해 단계로 복귀해 분할을 검토한다. 서술을 돕는 역할 유형 어휘를 프로세스 문서에 제공한다: 정보 보관자 / 서비스 제공자 / 조정자 / 흐름 제어자 / 경계 접속자 / 구조 조직자 — 분류 강제가 아니라 서술의 출발점.
* **구조 설계(structural)**: 모듈 내부 조직을 무정형으로 발명하지 않는다 — 알려진 구조 양식(계층, 파이프-필터, 중개자, 저장소 중심 등)의 이름을 대고 그 변형으로 서술한다. "어떤 양식을 왜 골랐고 어디를 바꿨는가"가 서술의 골격. 수준은 컴포넌트까지 — 클래스·함수·파일 금지 유지.
* **행위 설계(behavioral)**: 이 모듈이 관여하는 핵심 시나리오들을 하나씩 **걸어본다(walkthrough)** — 각 스텝에서 어느 모듈이 행동하고, 무엇을 누구에게 요구하며, 무엇을 넘겨받는지를 추적해 기술한다. 모듈 간 인수인계 지점은 표시해 둔다 — Phase 2에서 Interface 의무로 수확되는 재료다. 상태를 보유하는 모듈은 상태 서술(상태 목록·전이·계기)을 추가한다 — 스펙 수준이며 코드 수준이 아니다.
* **근거(rationale)**: 자명하지 않은 구조·행위 선택마다 3항으로 기록한다 — 무엇을 결정했고 / 어떤 대안을 고려했으며 / 어떤 기준(드라이버 — 비기능 요구·Constraint·기존 규약)이 판정했는가. Convention Survey의 출처 명기와 근거 설명 의무가 여기 합류한다.
* 검증: 모듈의 REALIZED_BY로 걸린 모든 SR이 최소 1개 행위 워크스루에 등장하는가 — 등장하지 않는 SR은 설계가 그 책임을 아직 소화하지 못한 것이다. 워크스루가 분해와 모순되면(모듈을 건너 짚는 흐름, 할당과 다른 수행 주체) 설계를 고치거나 분해 단계로 복귀한다.
* phase 게이트(등록·웹 승인 1회는 여기서): 분해 게이트(핵심 SR 커버, 고아 없음, 의존 무사이클, Constraint 준수) ∧ 모든 ModuleDesign에 설계 4항 충족 ∧ 모든 REALIZED_BY SR이 ≥1 워크스루에 등장 ∧ 워크스루-분해 모순 없음.

### Phase 2 — Contracts

계약은 Phase 1의 행위 워크스루에서 **수확**한다 — 워크스루에 표시된 모듈 간 인수인계가 Interface 의무의 원천이고, 경계를 넘는 데이터가 DataSchema의 후보다. 워크스루에 없는 계약 항목은 근거를 물어야 한다.

* Interface는 시그니처 나열이 아니라 **의무의 분배**를 기술한다: 호출자가 보장해야 하는 것(사전), 모듈이 보장하는 것(사후), 항상 성립하는 것(불변). 이 3항이 서술 골격이다.
* 최소 공개 원칙: 인터페이스는 숨긴 것의 나머지 전부가 아니라 소비자가 필요로 하는 최소다. 각 공개 항목에 **누가 소비하는가**를 명시하고(워크스루가 답을 이미 갖고 있다), 소비자를 댈 수 없는 항목은 과잉 노출 신호로 제거를 검토한다. 외부 표면이 없는 순수 내부 모듈은 Interface를 만들지 않는다.
* 계약 형식은 모듈 유형에 감응한다: 서비스는 엔드포인트 계약, CLI는 명령·인자 스키마, 라이브러리는 공개 함수 계약, 파서는 입력 문법 — 유형에 맞는 형식으로 기술하되 수준은 계약까지, 구현 코드는 금지.
* DataSchema는 DomainEntity의 1:1 복사가 아니다. 도출 질문 셋으로 구조를 정한다: 식별성이 필요한가 / 값의 동등성만 필요한가 / 함께 일관성이 유지돼야 하는 묶음인가(묶음이면 하나의 스키마 단위). REQ의 검증 규칙(형식·범위·필수성)을 스키마 제약으로 반영한다.
* 같은 데이터를 두 스키마가 다르게 정의하지 않는다 — 계약 간 정합을 phase 종료 전에 대조한다.
* 게이트: 외부 표면을 가진 모든 모듈에 Interface ≥1 ∧ 워크스루의 모든 인수인계가 어떤 계약에 소화됨 ∧ 모든 DataSchema가 유래 DomainEntity를 참조 ∧ 계약 간 모순 없음.

### Phase 3 — Task Decomposition

* 커버리지는 양방향이다: 모든 ModuleDesign이 ≥1 task로 분해되고(누락 없음), 모든 task가 ≥1 ModuleDesign에 소속된다(부모 없는 작업 없음). 소속 없는 작업은 어떤 이유로도 만들지 않는다.
* **복수 부모는 허용하되 규율이 있다**: 본질적으로 여러 모듈에 걸치는 작업(통합 테스트, 모듈 간 배선·연동)은 관련 ModuleDesign 전부를 부모로 갖는다 — 하나를 자의적으로 고르지 않는다. Ready 계산은 모든 부모의 상향 사슬 합집합 all-green이므로, 통합 작업이 관련 스펙 완성 전에 착수되지 않는 순서가 저절로 성립한다. 단, 판별을 먼저 한다: 걸침의 대상이 작업이 아니라 **구조물**이면(공용 버스, 빌드·도구 인프라, 공통 보일러플레이트) 다중 부모가 아니라 그것을 숨기는 결정 단위로 삼는 순수 기술 ModuleDesign의 누락 신호다 — Phase 1로 복귀해 모듈을 세우고 단일 부모로 붙인다. "거의 모든 모듈에 걸치는 태스크"는 항상 이 누락 신호로 취급한다.
* 태스크 품질 4기준: **독립**(태스크 간 의존을 최소로 — 필요한 의존만 depends on으로 명시, 사이클 금지) / **방법 비지정**(무엇이 완성되는지를 쓰고 어떻게 만들지·어느 파일인지는 쓰지 않는다 — 경로는 실행 회전의 발견 사항) / **추적**(task는 AC를 0개 또는 1개만 target한다 — 아래 AC 커버리지 규칙 참조) / **크기**(한 실행 회전에서 완결 가능한 분량 — 이보다 크면 분할, 이보다 잘게 쪼개 의존 사슬만 늘리지 않는다).
* 순서·병렬은 저장하지 않는다: 선행 관계만 depends on으로 기록하면 착수 가능 여부와 병렬 가능 집합은 보드가 계산한다. "기반 작업" 같은 분류 라벨을 만들지 않는다 — 많은 태스크가 의존하는 태스크는 그래프에서 저절로 먼저 선다.
* **AC 커버리지 규칙 (핵심 제약)**: 카디널리티는 task→AC 0..1(한 task는 AC를 안 겨냥하거나 정확히 하나만), AC→task 1..N(한 AC는 여러 task가 나눠 겨냥 가능). **phase 종료 시 계획 범위 안의 모든 AC(시나리오 부착·REQ 부착 공통)가 ≥1 task에 의해 target되어야 한다** — target되지 않은 AC가 남으면 계획이 완결되지 않은 것이다. 미커버 AC 발견 시 그것을 닫을 task를 추가 도출한다(어느 모듈 소속인지는 워크스루가 알려준다).
* AC를 target하지 않는 task(준비 작업·내부 정비 등)는 허용되나, 그 완료 판정은 대상 AC closed로 계산할 수 없다 — 데몬의 task 완료(isCompleted) 정의 현재 상태와 대조하고, 0-AC task의 완료 기준이 미정이면 보고 후 질문한다.
* 게이트: 양방향 모듈 커버리지 ∧ depends on 무사이클 ∧ task→AC 카디널리티 준수 ∧ **범위 내 미target AC 없음** ∧ 승인 후 보드에서 최소 1개 task가 Ready로 등장함을 확인.

## 작업 결정 (기본값 — 구체 계획 단계에서 사용자와 확정 후 진행)

1. 태스크에 파일 경로 불포함(위 4기준의 기본값). 확정 질문 1회.
2. Convention Survey의 Constraint 승격은 /shall:specify 수정 모드 왕복이 원칙(플레인 소유권 유지), 같은 세션에서 연속 수행.
3. ImplementationTask의 엣지·frontmatter 표현은 발명하지 않는다 — 데몬 현재 스키마(기반 확인 2)를 따르고, 부재 시 보고 후 질문. **부모 카디널리티(복수 ModuleDesign 허용)와 Ready의 합집합 사슬 계산이 데몬 현재 구현과 일치하는지 확인** — 단일 부모 전제가 박혀 있으면 확장이 필요한 지점으로 보고.
4. 분해·설계는 승인 규약 사유로 한 phase에 통합됐다(같은 노드의 웹 2회 승인 회피). 남은 통합 후보는 2·3이며 도그푸딩에서 재평가 — 내부 전용 모듈뿐이면 Phase 2가 공집합 통과하므로 분리 비용은 낮다.
5. **승인 타이밍**: 등록·웹 승인은 phase 종료마다 1회, 총 3회. Phase 1 내부의 분해 중간 승인은 터미널 전용이며 파일 등록 없음 — ModuleDesign은 설계 4항까지 채워진 완전체로 한 번만 등록·웹 승인된다. 수정 모드에서 설계만 고치는 경우에도 같은 규약(개정 → 자동 yellow → 재승인)이 자연 적용된다.

## 산출물

1. `docs/Shall_Plan_Process_v1.md` (영어) — specify 프로세스 정본과 같은 형식: 입력·진입 디스패치·공통 규율(Convention Survey·근거 설명 의무 포함)·Phase 1~3(스텝 ordered list + 주의 불릿 + 복귀 경로 + 게이트). 위 설계 지침의 규칙이 스텝 안에 행동으로 녹아 있어야 하며 고유명사는 없어야 한다.
2. 플러그인 증분 — `commands/plan.md`(얇게: 입력·게이트 확인·디스패치·위임), `skills/shall-plan/`(SKILL.md + references/phase-1~3.md), shall-authoring 스킬에 plan 노드 4종 저작 규약 추가(스키마 재기술 금지 원칙 유지).
3. CLI 증분 — add-spec-node에 plan 노드 4종 템플릿(선택 필드·enum은 주석), check에 plan 게이트 검사(고아 ModuleDesign, 모듈·태스크 의존 사이클, task의 대상 AC 참조, 계약 정합은 가능한 범위), 에러 메시지 교육화 동일 적용.
4. 상시 층(`.shall/GROUND.md`)에 plan 플레인 불가침이 추가로 필요한지 검토 — 필요 최소만.
