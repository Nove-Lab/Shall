# Shall — /plan Process (v2)

> The agent–human interaction flow that fills the plan plane — modules, the contracts between them, and the work items the board hands out — on top of a specification a person has approved, in two stages: a planning stage that writes nothing, and a transcription stage that writes everything at once. Written in the graph's own relation names from the first line, so nothing here has to be translated before it is followed. Where this document and the code disagree, the code is right. v1 (2026-08-19) ran three phases, each approved in the browser before the next; what that produced on a real project was a plan that named no technology, a template filled with figures of speech, and work items nobody could pick up, and v2 (2026-08-23) is the answer: the agent plans first, the way it plans anything, and Shall takes the transcript.

## Input

* Invocation form: `/plan [--auto] <technical direction or change request>` — the user's input is passed as the command argument (the `$ARGUMENTS` slot in the agent template).
* `direction`: the user's natural-language statement of how the approved specification should be built, or of what about an existing plan should change. The user does not declare which; entry dispatch determines it.
* If the input is empty, do not start the process; ask for the direction first. The run spends the user's attention, and a run spent on a guessed direction costs more than one question.
* `--auto` removes the two terminal stops of stage 1 — the technology confirmation and the agreement on the whole plan — and nothing else. The exploration, the design, the questions that genuinely need the user, the transcription, the check and the one browser judgment are unchanged.

## Entry Dispatch

1. Read the state of the whole project, band by band. Unapproved plan work comes first: anything yellow in the plan band is a run somebody started and nobody agreed to, and it is finished or set aside before this request opens a new one.
   * An `Assumption` a `Module` assumes is filed with the intent band, because `Assumption` is the one type the canon gives no layer of its own; it belongs to the run that wrote it.
   * A `SystemResponsibility` that is yellow **because it changed** — and that now carries an `IS_REALIZED_BY` relation — is this process's own unapproved work, not the specification's. One yellow because nobody has ever approved it belongs to `/specify`; the two are told apart by which of the two reasons the read gives.
   * A yellow `Decision` is left standing whichever process wrote it: a person's dictation through `/raise` waits on its own approval, and a technology decision a broken-off run wrote is covered by the one approval at the end of this one.
   * Under `--auto` nothing is asked here: name what is yellow, go on, and say that the one approval at the end covers the older work as well.
2. Check the upstream gate. The plan plane is written on top of an approved specification, and the check is local to the subgraph this direction touches rather than to the whole project.
   1. The shortcut: if nothing in the intent band is any color but green, the gate is passed and no walk is needed.
   2. The walk: for each `SystemResponsibility` this direction reaches, read its own color, then walk **up** — the `Scenario` that `DERIVES_RESPONSIBILITY` to it, the `UseCase` that `DETAILS` that scenario, the `Actor` that `PERFORMS` the use case, the `Goal` that is `PURSUED_BY` that actor, and any `Goal` that `REFINES` it — and **sideways** — the `Requirement`s the responsibility `REQUIRES`, each requirement's `AcceptanceCriterion` and `Constraint`, and the criteria the scenario carries. Every one of them must be green.
   3. If any of them is not, name those ids to the user, say the specification has to be settled first, and stop. Do not plan over a specification a person has not agreed to: the plan would be rewritten by the judgment, and the work is thrown away.
   * This is the same set of nodes a work item's readiness is computed over, which is why the gate is exactly this walk and not a wider one.
3. Determine the mode. A responsibility in scope with no `IS_REALIZED_BY` relation out of it has no module yet → **new mode**: stage 1 from its first step. Otherwise → **revision mode**.
4. (Revision mode) There is no layer to enter at. Stage 1 opens with the reach: from the status already read, walk the relations out from what the direction names until nothing new turns up — the modules, their contracts, the work items they allocate, the criteria those target, the responsibilities above — and that set is what stage 1 redesigns **as a whole** and what stage 2 rewrites. A boundary, a contract and the work under it are one design, so they are reconsidered together and never by entering one layer.
   * Surgical change first: keep and revise the nodes that are there, additions are allowed, deletions only on the user's explicit request.
   * A direction about one work item still runs the whole of stage 1 over that reach; what is small is the reach, not the procedure.

## 0. Common Rules

* **Question rule**: at most four questions per round, each offering 2–4 options plus a free-form answer, the recommended option first. A question you could answer correctly yourself is not a question.
* **Default rule**: an ambiguity a reasonable default can carry is not asked about — it is recorded as an `Assumption` and anchored with `ASSUMES` from the node that assumes it. In this plane **only a `Module` may assume**: a contract's or a work item's default is hung on the module that owns it, and a default with no module to own it is asked about instead.
* **Full-resolution rule**: an ambiguity or conflict no default can carry is resolved by questions inside stage 1 — the plan is not presented over an open point.
* **Concreteness rule** (replaces v1's level rule): **decisions and contracts in the spec, bodies in the repo.** Intent says what and why and names no technology. A `Module` names its technology by its standard names — runtime, language, storage, the core libraries; the project-wide stack is a `Decision` the modules refer to — its structure as components and the lines between them, its contracts at signature level (name, inputs, outputs, errors), its behaviour, and the alternatives it refused; never a function body, pseudocode or a list of files. A `WorkItem` says its scope, the criteria it targets, what it waits on and its definition of done — and never the method: no file list, no function design, no procedure; those are found in the repository at work time and recorded in the work log's `Approach`. A figure of speech standing where a technology should be is a decision deferred to the first turn of work, where it is made again and recorded nowhere. The one exception is still the user's: if the direction asks for paths in so many words, confirm it once, record them in the work item's `Notes`, and say in the presented plan that the rule was relaxed on request.
* **Incremental declaration**: work items are declared for what is visible now; more come through `/plan` again in revision mode, and the module they hang off comes back to the queue because its `ALLOCATES` line moved. Nothing requires the whole decomposition up front.
* **The one `Decision` this process writes**: a project-level technology choice confirmed in stage 1, filed as a `Decision` with `AFFECTS` at every `Module` it binds. Every other decision is a person's, dictated through `/raise`; a revision of the specification that planning argues for is a direction in words and a round trip through `/specify`.
* **Fix Spec first**: at the start of stage 1, at the start of stage 2, and when work resumes after the browser wait, read what the board says is red and clear it before writing anything new.
* **Convention Survey**: before the first boundary is drawn, read the project's own documents — its readme, a contributing guide, anything under a docs folder, a design record, the rules file the project loads into every session — and sort what bears on this plan three ways: (a) a norm that genuinely **binds** is promoted to a `Constraint` through `/specify` in revision mode, in this session, because an outside document can be revised without anything in the graph turning a color; (b) a **design convention** is followed, and the node whose design followed it names the document's path in its own body; (c) a **conflict** between the user's direction and a convention is put to the user as an option question and never settled silently. If the project has no such documents, say so once, ask once whether there is an unwritten convention worth honoring, and go on.
* **Grounds duty**: where an outside document or a piece of investigation actually made a design decision, the plan presented at the end of stage 1 says **which decision followed which grounds**, naming the source, so that nobody agrees to a decision without having seen what produced it. The node's body carries the same reasoning in full.
* **Gaps in the specification are the normal path.** Planning is where a missing responsibility, an unjudgeable criterion or a term pulling two ways is discovered. The return path is `/specify` in revision mode: take the gap there, let it be approved, and resume at the step stage 1 left.
* **No stored backlog**: every work item belongs to a module — `Module —ALLOCATES→ WorkItem` is the one relation that holds a work item, and `shall check` reports one no module allocates as an orphan — and nothing is planned that the specification does not ask for. The place for a verification scenario is an acceptance criterion; the place for an end-to-end proof is the evidence the execution plane records.
* **Approval principle**: a change to an approved node is a revision of that node's file, not a second node saying the newer thing.
* **Three words this document does not use.** It does not say the plan is *registered* in a database — the plan is files. It does not say a type has *fields* — a node's body is free markdown, and the starting file the tooling writes is the only place that suggests a shape for it. And it never says "the card": a run arrives in the queue as one or more cards.

## 1. Stage 1 — Planning (outside Shall's jurisdiction; writes nothing)

1. Run the **Convention Survey** and sort what it finds three ways. Finish the promotion round-trip for anything in (a) before the boundaries lean on it.
2. **Read the code that is there, read-only** — the layout, the entry points, the modules already standing, the tests and how they run, the build. What exists is a driver as hard as any requirement: a boundary the code already draws is followed unless the direction says to move it, and then the moving is said in the plan.
3. **Technology step.** Scout what the project already runs on — manifests, lockfiles, build and test, the rules file, the code — and the stack the intent recorded in assumptions or constraints; propose the stack for what this direction builds, by the standard names and with the alternatives weighed; **terminal stop A**: put it to the user as an option question and take the answer. Under `--auto` the question is not asked: take what the repository already runs on, or what the direction names, and say which and why. A choice that holds for the whole project becomes the `Decision` of the Common Rules; a choice that is one module's own is written in that module's `Technology` section and nowhere else.
4. **Collect the drivers**: every green `SystemResponsibility` in scope, plus the non-functional `Requirement`s and the `Constraint`s that bind them. The drivers are read and not recorded as relations — the canon draws none between a `Module` and a `Requirement` or a `Constraint` — which is why the grounds duty exists.
5. **Decompose from responsibility to structure, never the other way.** Ask of each candidate module what would change inside it that the rest must never see — the storage it writes to, the outside system it speaks to, the algorithm it applies, the format it parses; a candidate that can only name where it sits has not justified its boundary. That question is a test run in the conversation, not a section written in the node: what the module keeps to itself shows in its `Technology` and its `Decisions`. Verify each assignment twice — do the responsibilities change for the same reason, and does every dependency between modules run through a contract. Settle a contested responsibility by information. A purely technical module is legitimate. If one `Term` is asked to mean two things in two modules, stop and let the user settle whether the term splits or the boundary moves.
6. **Design each module in the six parts the starting file suggests** — responsibility, technology, structure, contracts at signature level naming the `Interface` each belongs to, behavior walked through the key scenarios with every hand-over between modules marked, decisions as the alternatives refused — derived from the approved scenarios and responsibilities and written in the world's names. Check the design against the assignment: every responsibility a module realizes appears in at least one walkthrough.
7. **Harvest the contracts from the walkthroughs.** Every hand-over is the origin of an `Interface` obligation — what the caller guarantees first, what the module guarantees in return, what holds either way, and the protocol — and every piece of data that crosses a boundary is a candidate `DataSchema`, derived with three questions (an identity, a value compared whole, or a bundle kept consistent) and naming its concept with `REPRESENTS`. Name the consumer of every published item and remove what has none; a module with no outside surface publishes nothing. The module's `Contracts` section and the `Interface` node say different things about one boundary — the shape in the module, the obligations in the interface — and neither is copied into the other.
8. **Cut the work.** Every module in scope gets at least one `WorkItem`, or the plan says its work is not visible yet; every work item belongs to a module — one by rule, several only for work that genuinely lies between them, and work that seems to touch nearly every module is a common module nobody has drawn. Hold every work item to the tests: independent (as few `DEPENDS_ON` as the work allows, and no loop), sized to one turn of work, aimed at none, one or several criteria as its definition of done makes judgeable, carrying a definition of done that says observably what is built and what it does — never the criterion's sentence again — method-free, stated as work, and declared only when visible. Store no order and no labels: precedences are `DEPENDS_ON` lines, and what can be started is computed from them. Cover the criteria: every `AcceptanceCriterion` in scope is targeted by at least one work item.
9. **Check the draft against itself**: every responsibility in scope reaches at least one module; no module hangs off no responsibility; no cycle among module dependencies through consumed contracts; nothing breaks a constraint; every criterion in scope is targeted; every work item belongs to a module; no work item names a path, a class, a function or a procedure; no definition of done repeats a criterion's sentence; no figure of speech stands where a technology should.
10. **Present the whole plan in the terminal** — the stack and what it binds, every module with the responsibilities it realizes and the technology it stands on, every contract, every work item with its module, its targets, its waits and its definition of done, and the grounds that decided what — and get **one yes (terminal stop B)**. On a no, take the objection back to the step it names and present again. Under `--auto` the plan is written out in full and not waited on. Nothing reaches disk before this step passes.

## 2. Stage 2 — Transcription (Shall's)

1. Write in an order that keeps every anchor's far end alive before the check: `Module` files first, then the `IS_REALIZED_BY` line in each responsibility that realizes them (the module's anchor lives upstairs); the technology `Decision`, if any, with `AFFECTS` at every module it binds, written after the modules so every line reaches a file that exists; `Interface` then `DataSchema` — `EXPOSES`/`CONSUMES` in the module's file, `CARRIES` in the interface's, `REPRESENTS` in the schema's; `WorkItem` files, then the `ALLOCATES` line in each parent module, with `DEPENDS_ON` and `TARGETS` in the work item's own file; `ASSUMES` in the module's file; `MENTIONS` sparingly, from the node being written.
2. Run `shall check` — scoped while iterating, whole before handing over — until it exits 0. A file that will not read is not in the graph at all.
3. Tell the person that one or more Spec approval cards are waiting in the Review Queue — one per responsibility that gained a module, carrying everything below it; one at the technology decision when there is one, carrying every module it `AFFECTS`; a work item alone in a card does not happen, because one no module allocates is red and outside the queue — and that `shall` with no arguments opens it. Say it; do not run it. Then stop and wait.
4. On return, read `shall status --json` over every id this run wrote or changed. Still yellow: name those ids once and wait again. Red with a standing rejection: read the rationale whole, revise that file — the rejection lapses by arithmetic when the content changes — and wait again. The run is never closed on a partial pass.

## 3. The End

* Gate, answered from the CLI and computed by nobody: every criterion in scope is targeted by some work item (`shall status --json`, joined by hand); every module has at least one work item, or the presented plan said its work is not visible yet; nothing is red (`shall check` — an orphan work item, a loop, an off-target claim); something can be started (`shall board --json`, the Implement half not empty — read after the approval in both modes, because readiness is computed over a chain that is this run's own yellow until then).
* Declare the plan finished, name the work items the board says can be started, and log it once: `shall log plan_done "<summary>" --refs <ids>`, the summary counting the ids this run wrote or revised by type (`Plan finished — Module 2, Interface 3, WorkItem 6`).
* Changes to the plan after this come back through `/plan <change request>`, which enters in revision mode: stage 1 over the reach, stage 2 over the files.

## 4. Invariants

Decisions and contracts in the spec, bodies in the repo · no method in a `WorkItem` · incremental declaration · no relation joins two modules (a dependency is a consumed contract) · `ASSUMES` from `Module` only · every work item allocated by at least one module, and the check says so · `TARGETS` none, one or several · the one `Decision` this process writes · nothing reaches disk in stage 1.

## 5. Relation table

| The process says | The canon has | Written in |
|---|---|---|
| a responsibility gains a module | `SystemResponsibility —IS_REALIZED_BY→ Module` | the responsibility's file |
| a module publishes a contract | `Module —EXPOSES→ Interface` | the module's file |
| a module calls a contract | `Module —CONSUMES→ Interface` | the calling module's file |
| a contract carries data | `Interface —CARRIES→ DataSchema` | the interface's file |
| a schema comes from a concept | `DataSchema —REPRESENTS→ DomainEntity` | the schema's file |
| a module is given a piece of work | `Module —ALLOCATES→ WorkItem` — the one relation that holds a work item | the module's file |
| a work item waits on another | `WorkItem —DEPENDS_ON→ WorkItem` | the waiting work item's file |
| a work item aims at criteria | `WorkItem —TARGETS→ AcceptanceCriterion` — none, one or several | the work item's file |
| the stack binds a module | `Decision —AFFECTS→ Module` — the one decision this process writes | the decision's file |
| a default recorded as an assumption | `Module —ASSUMES→ Assumption` | the module's file |
| a term used in prose | `MENTIONS → Term` | the mentioning node's file |
| a module depending on another module | nothing — no relation joins two modules | — |
| a module answering to a requirement or a constraint | nothing — no relation joins them either | — |
