# Shall — work · raise 스킬 구현 명세 (execution plane)

사용자가 에이전트와 Shall을 쓰는 두 개의 동급 진입점을 구현한다:

- **`/shall.work`** — 보드에서 일을 찾아 개발하고 Journal 트리로 보고하는 사이클.
- **`/shall.raise`** — 사용자의 물음표("이상한데", "점검해야 하나")에 대한 탐색·진단·착지.

현재 구현된 CLI(`shall board`·`status`·`check`·`add-spec-node`, `--json`)와 확정된 스키마(TaskCompletionReport·Evidence·Finding·Decision)를 전제로 한다.

## 0. 원칙

- **스킬은 얇다 — 절차와 판단 기준만 담는다.** 문법 강제는 스킬이 아니라 로더의 스캔(문법 위반 = red)이 한다. 스킬 본문에 스키마 상세를 복제하지 않는다 (드리프트 방지 — 필요한 형식은 `add-spec-node`와 기존 노드 파일을 참조하게 한다).
- 에이전트의 파일 저작 표면은 `.shall/spec/` 뿐이다. ledger 쓰기·spec 파일 삭제(rm)는 금지 (deny 규칙과 일치). 삭제는 deletionProposed frontmatter로 제안한다.
- 에이전트가 쓴 노드는 자동으로 yellow다 — 등록 절차 없음. green의 제조는 사람의 웹 승인뿐이며, 스킬은 승인을 대행·위조하지 않는다.
- 사용자와의 단순 문답은 터미널 대화로 소화하고 Shall에 올리지 않는다. Shall에 도달하는 것은 노드 저작뿐이다.

## 0-b. 선행 스키마 수정 — Finding 소속의 선택화

현재 구현은 Finding이 WorkLog에 반드시 연결되도록 되어 있다. 스킬 구현 전에 먼저 고친다 (스키마·검증·로더 전 계층):

- **Finding의 WorkLog 소속(연결 엣지)을 필수 → 선택으로 변경한다.** 소속은 태생을 따른다: 회전 중 발견(report 저작)은 해당 WorkLog에 연결, 회전 밖 발견(raise 저작)은 연결 없는 단독 Finding. 가짜 소속을 만들지 않는다.
- **Finding을 고아(red) 판정 제외 타입에 추가한다** — 소속 없음이 정당한 상태다 (Goal·Term과 같은 목록).
- **검증 정책에서 "Finding은 WorkLog 필수" 류의 조항을 제거**하고, `shall check`가 단독 Finding을 통과시키는지 확인한다.
- **리뷰 큐**: 어느 Journal 서브트리에도 속하지 않은 yellow Finding을 "단독 발견" 항목으로 노출한다 (Work Report 번들과 별개. blocking이면 기존 우선 노출 규칙 적용).
- 메타모델 팝업 등 소속 규칙을 표시하는 곳이 있으면 함께 갱신한다.

## 1. 커맨드 구성

```
/shall.work           작업 사이클 전부 — 인자: --auto (무정지), --dry (예보)
/shall.work.todo      확인만 — 읽기 전용
/shall.work.report    보고만 — 단독 호출 시 일괄 재구성
/shall.raise          물음표의 진입점 — 사이클 밖, work와 동급
```

- 파일명 = 호출명 (`.claude/commands/shall.work.md`, `shall.raise.md` 등). work의 구성품은 단독 실행 가능해야 한다 (합성 안에서도, 낱개로도 같은 부품).
- raise는 work 네임스페이스 밖이다 — 사이클의 구성품이 아니라 상시 진입점이므로.
- 각 커맨드는 CLI의 `--json` 출력을 소비한다. 화면 문자열 파싱 금지.

## 2. `/shall.work.todo` — 확인

읽기 전용. 쓰기 0.

1. `shall board --json` — Fix Spec / Implement 목록 수집.
2. `shall status --json` — red·yellow 현황, 미응답 blocking Finding.
3. 사용자에게 보고: ① 미응답 blocking Finding (있으면 최상단 — 잠금은 아니지만 우선 확인 대상), ② Fix Spec 목록 (반려 rationale 요약 포함), ③ Implement 목록 (Ready만), ④ 리뷰 대기(yellow) 적체 규모 한 줄.
4. 아무것도 실행하지 않고 종료. "다음 행동" 제안은 한 줄까지만.

## 3. `/shall.work.report` — 보고

산출: Journal 1개를 뿌리로 하는 트리. **한 회전이 여러 항목을 잡았어도 Journal은 1개 — 항목마다 WorkLog가 갈라진다.**

**트리 조립 규칙 (스킬 본문에 이 절차 판단을 담을 것 — frontmatter 필드 상세는 여전히 기존 파일 참조)**:

- **Journal** ⊃ (CONTAINS) **WorkLog** 여럿 — 선택한 작업 항목마다 하나.
- **Journal의 본문 최상단 섹션은 "User Prompt"** — 이 회전을 시작시킨 사용자의 최초 발화를 **그대로(verbatim) 기록한다. 요약·의역 금지.** (--auto라면 그 호출 명령이 곧 발화다.) 노드 템플릿(`add-spec-node` 산출 골격)에 이 섹션을 추가하는 작업을 포함한다.
- WorkLog가 implementation task를 대상으로 했다면 **WorkLog → 그 task를 엣지로 연결**한다.
- 그 작업으로 계획된 implementation task를 **모두 마쳤다고 판단되면 TaskCompletionReport를 달고, TCR → 그 task를 엣지로 가리킨다.** (부분 진척이면 TCR 없이 WorkLog 서술까지만.)
- WorkLog의 대상 task가 겨냥하던 AC들 중 **닫을 수 있다고 판단되는 것이 있으면, 해당 AC마다 Evidence를 별도 작성하고 Evidence → 그 AC를 엣지로 가리킨다.** (AC 하나에 Evidence 하나 — 여러 AC를 한 Evidence로 뭉치지 않는다.)
- 작업 중 예상하지 못했던 것을 발견한 경우, **다음 두 조건 중 하나 이상이 성립할 때만** Finding을 작성하고 해당 WorkLog에 연결한다 (회전 중 발견이므로 소속이 실재한다):
  - ① **다음 작업자(다음 세션 포함)에게 전달될 필요가 있는가** — 모르면 헛수고·재발이 생기는 것.
  - ② **스펙·계획의 변경이 필요한 사안인가** — 사람의 결정(Decision) 재료가 되는 것.
  - 둘 다 아니면 Finding이 아니다 — 예상 밖이었더라도 그 자리에서 해결하고 넘어갔고 아무것도 바뀔 게 없으면, WorkLog 본문의 서술로 충분하다. **독자 없는 노드는 쓰지 않는다.**
  - 스펙·계획에 이미 적혀 있거나 알려진 사항, 통상적 구현 세부, 에이전트 재량 범위의 선택은 애초에 발견이 아니다.
- 커밋은 노드가 아니라 WorkLog frontmatter의 sha 목록이다.
- 엣지의 정확한 이름·방향은 스키마(허용 엣지쌍)를 따른다 — 스킬 본문에 엣지 이름을 하드코딩하지 말고 참조로.

**입력 이중 신분**:
- **사이클 안** (work 합성 중): 개발 구간에서 수집한 노트(작업 내역·커밋·검증 결과·관찰 메모)로 트리를 저작.
- **단독 호출**: "보고 안 된 것"을 스스로 찾아 재구성한다 —
  1. `git log <마지막 Journal 시점>..HEAD` 로 커밋 수집. Journal이 하나도 없으면 범위를 사용자에게 묻는다.
  2. 커밋·변경 파일을 스펙에 대조해 "이 커밋들은 어느 task/REQ 계열" 후보 매핑. 확신 없는 매핑은 질문으로.
  3. **git 밖도 훑는다**: 스펙 쪽에서 역방향으로 — 진행 중이던 task 중 완료된 듯한 것, open AC 중 닫을 근거가 있어 보이는 것 — 을 점검하고, 커밋 없는 작업(검증 실행, 조사 등)이 있었는지 사용자에게 한 번 묻는다.
  4. WorkLog 초안 + task를 끝냈으면 TaskCompletionReport, AC를 닫을 만하면 Evidence 초안 제안.
  5. 사용자와 대화로 교정 후 확정.

**공통 절차**:
1. 트리 초안을 터미널에 요약 제시 — WorkLog n건, TCR·Evidence·Finding 각 대상 명시. **[정지: 사용자 확인]**
2. 확인 후 `.shall/spec/execution/` 하위에 낱장 기입 (형식은 `add-spec-node` 또는 기존 파일 참조).
3. `shall check --scope .shall/spec/execution` 으로 자기 검증 — red(문법)가 있으면 즉시 수정.
4. "리뷰 큐에 Work Report로 올라감. 웹에서 접수 가능"을 안내하고 종료 — **웹 접수를 기다리지 않는다** (비동기).

**Evidence 주의**: 이미 closed인 AC에 Evidence를 추가하면 그 AC의 닫힘이 자동 실효되어 재심사가 유발된다. 의도한 재심사가 아니면 붙이지 말고, 붙이려면 사용자에게 그 효과를 알리고 확인받는다.

## 4. `/shall.work` — 한 사이클 (합성)

```
todo → [정지 1: 선택 확인] → 개발 (무정지) → [정지 2: 보고 확인] → report → 종료
```

1. **todo 로직 수행** 후 착수 대상 제안 — **이번 회전에서 함께 잡을 작업 묶음**을 고른다:
   - 후보 우선순위: Fix Spec 먼저, 그다음 Implement 상단부터. (보드에 뜬 항목은 이미 착수 가능 판정이 끝난 것 — depends on·사슬 green 재검사 불요.)
   - **개수: 기본 최대 3.** 신중한 진행이 낫다고 판단하면 1개만 제안해도 된다. 사용자가 명시적으로 더 많이 요구하면 3을 넘겨도 되나, 그때 "권장 최대는 3"을 한 번 고지하고 따른다.
   - 잡은 작업들을 어떤 순서로·어떻게 진행할지는 에이전트 재량이다 — 스킬은 개수만 다룬다.
2. **[정지 1]** 터미널에서 선택 확인 — 무엇을(ID 목록), 왜(항목당 한 줄). 사용자가 조정하면 따른다.
3. **개발**: 선택 묶음 수행. 항목별 작업 노트를 구분해 수집한다 (WorkLog가 항목별로 갈라지도록 — 3개를 잡았으면 Journal 1개에 WorkLog 3개).
   - **이 구간은 Shall이 방법을 가이드하는 영역이 아니다 — 스킬 본문에 이를 명시할 것.** 개발의 방식·품질 기준·도구는 에이전트가 원래 최선이라 여기는 방식과, 이 프로젝트에 이미 존재하는 컨벤션·프로세스(CLAUDE.md, 코딩 규칙, 테스트·커밋 관례 등)를 따른다. Shall의 문법·절차는 이 구간에 개입하지 않으며, Shall이 요구하는 것은 구간의 양 끝뿐이다 — 들어갈 때 스펙(task·REQ·AC)을 읽는 것, 나올 때 보고 재료(노트·커밋·검증 결과)를 들고 오는 것.
   - Implement: 대상 task의 ModuleDesign·REQ·AC를 읽고 구현. 커밋 해시·검증 실행 결과·관찰을 작업 노트로 수집 (report의 재료).
   - Fix Spec: 반려 rationale/문법 위반 내용대로 스펙 파일을 수정 (→ yellow, 재승인 대기). 스펙만 고친 회전도 회전이다 — 보고까지 간다.
   - 개정·전달감 발견 시 (§3 Finding 조건): 노트로 수집 — report가 해당 WorkLog에 연결된 Finding으로 저작한다. raise를 호출하지 않는다. **blocking 사안이면** 해당 항목을 중단하고 사용자에게 알린다 — 다른 항목으로 전환할지, 회전을 접을지는 사용자와 정한다.
   - 이 구간에서 사용자에게 묻는 것은 진행 불가 시(설계 선택 등 재량 밖)에 한한다.
4. **[정지 2]** report 로직의 트리 초안 확인 (§3 공통 절차 1).
5. **report 로직으로 기입·자기 검증·안내 후 종료** (§3 공통 절차 2~4).

**중단·재개**: 개발이 세션을 넘겨 끊긴 경우의 복구 경로는 단독 `work.report`다 — git 재구성이 잃어버린 노트를 대신한다. 별도의 노트 영속화 장치를 만들지 않는다.

## 4-b. `/shall.work --auto` — 무정지 모드

work의 인자 분기다. **정지 1·2를 생략하고 todo → 선택 → 개발 → report 기입까지 완주**한 뒤, "웹에서 확인·승인하시거나 질문하세요"로 끝난다.

- 안전 근거: 산출물은 전부 yellow — 중간 확인을 생략해도 판정은 생략되지 않는다. 웹 승인(리뷰 큐)이 유일하고 최종적인 관문으로 남는다. --auto는 확인 시점을 중간에서 최후 1회로 통합하는 것이다.
- 선택: 정상 work와 같은 규칙 (Fix Spec 우선, 기본 최대 3) — 확인 없이 스스로 확정하되, 무엇을 왜 골랐는지는 Journal에 남긴다.
- **물을 일이 생기면 그 일은 하지 않는다**:
  - blocking 발견 → 해당 항목만 중단, Finding 기록, 나머지 항목 계속.
  - 재량 밖 판단 필요(설계 선택 등) → 임의로 정하지 않는다. 해당 항목 중단, 사유를 Finding 또는 노트로 남기고 나머지 계속.
  - 전 항목이 중단돼도 report까지는 간다 — "무엇이 왜 미완인가"도 보고다.
- report의 트리 초안 확인(정지 2)도 생략 — 기입 후 `shall check` 자기 검증은 동일 수행, red 발생 시 즉시 수정.
- 종료 메시지에 요약: 완료 n건 / 미완 m건(사유) / 기입된 노드 수 / "웹 리뷰 큐에서 확인·승인 또는 반려로 질문해 주세요".
- `--dry`와 `--auto`는 동시 지정 불가 (예보와 완주는 모순).

## 4-c. `/shall.work --dry` — 예보 모드

work의 인자 분기다. **정지도 개발도 없이, 읽기와 예측만으로 한 번에 출력하고 종료한다.**

1. todo 로직 수행 — 지금 무엇을 할 수 있는지 (Fix Spec / Implement 목록, blocking Finding, 리뷰 적체).
2. 착수 대상이 될 묶음(실제 work가 제안했을 그것)에 대해, **완수된다면 어떤 보고가 기입될지 예상 시나리오**를 출력:
   - 예상 트리 구조: Journal 1 ⊃ WorkLog ⊃ {TaskCompletionReport, 닫힘을 겨냥할 AC와 그 Evidence 후보}
   - 근거는 선택 항목의 스펙 관계(task → ModuleDesign → REQ → AC)에서 추론 — 지어내지 않고, 스펙이 말해주는 범위까지만.
3. **쓰기 0** — spec/·ledger/·git 어디에도 아무것도 남기지 않는다. 사용자 확인 정지도 없다.
4. 전 출력에 `[DRY]` 접두, 종료 시 "예보만 — 아무것도 기록되지 않았습니다" 명시.
5. 용도: 사이클 학습·온보딩, 착수 전 점검. work 도움말에 안내한다.

## 5. `/shall.raise` — 물음표의 진입점

**정체**: 사용자가 무엇을 해야 할지 모르는 채 던지는 물음표에 대응한다 — "결제 쪽이 좀 이상한 것 같은데", "이거 점검해야 하나", "이게 왜 이렇지". `/specify`·`/plan`("이거 해줘/고쳐줘" — 할 일을 아는 사람의 문)과의 차이가 이것이다. 언제든 부를 수 있고, 사이클과 무관하다.

**입력**: `/shall.raise <물음표>` — 사용자의 발화가 명령 인자로 전달된다 (`$ARGUMENTS` 자리 — /specify·/plan 커맨드에 이미 작성된 것과 같은 관례를 따른다). **입력이 비어 있으면 절차를 시작하지 않고 무엇이 궁금한지·이상한지를 먼저 묻는다.** 물음표 없는 raise는 탐색할 대상이 없다. (참고: work는 인자 없이 시작 가능하다 — 보드가 대상을 주기 때문. raise는 사용자의 발화가 곧 대상이다.)

**절차**:

1. **탐색** (읽기 전용): 물음표 주변을 조사한다 — 관련 스펙 노드와 색 상태, 열린 Finding, 최근 개정 이력, 해당 코드까지. `shall status`·`check`·grep·git 등 수단 불문. **이 단계에서는 어떤 파일도 쓰지 않는다.**
2. **진단 보고**: 무엇이 어떤 상태이고, 어긋남이 있다면 어디인지를 사용자에게.
3. **대화**: 사용자가 진단을 보고 판단을 형성한다 — 이 커맨드의 본체다. 개정 쪽으로 기울면 "어떻게 바꿀지"까지 확정됐는지 확인한다 (확정 전엔 Decision을 쓰지 않는다).
4. **착지** — 대화의 결말에 따라:
   - **(a) 개정 판단 확정** → Decision 저작 (사용자 판단의 받아쓰기) + AFFECTS 대상 노드 수정 (→ yellow, 재승인 대기).
   - **(b) 판단 유보, 전달 필요** → 단독 Finding 저작 — WorkLog 연결 없음. `blocking`(무언가를 막는 사안인가), `relatedNodes`(힌트 — 특정 못 하면 비워도 됨), 본문(무엇을 발견했고 왜 전달·개정이 필요한가 — 배경까지. 사람의 결정 재료다).
   - **(c) 둘 다** → Decision + Finding 모두 저작, Decision —RESOLVES→ Finding ("무엇을 봤나"는 Finding에, "어떻게 하기로 했나"는 Decision에).
   - **(d) 문제없음 확인** → 등록 없음. "확인했고 문제없음"으로 종료 — **실패가 아니라 정상 결말이다.** 물음표의 답이 안심인 경우도 산출이다.
5. 사이클을 시작하지 않는다 — "지금 구현할까요?"로 work를 끌고 들어가지 않는다. 개정된 스펙이 만들 작업은 승인 후 보드가 계산한다.

**Finding 성립 문턱 (§3와 동일)**: ① 다음 작업자(다음 세션 포함)에게 전달될 필요, 또는 ② 스펙·계획의 변경 필요. 둘 다 아니면 등록 없음 — 독자 없는 노드는 쓰지 않는다.

## 6. 금지 목록 (스킬 본문에 명시할 것)

- ledger(`.shall/ledger/`) 쓰기, spec 파일 rm/git rm, 승인·접수의 대행.
- 이미 승인된(green) 실행 기록의 수정 (append-only — 수정하면 yellow로 강등되어 재승인 유발).
- Decision 노드의 임의 저작 — 결정은 사람의 판단이다. 사용자가 대화에서 판단을 확정하고 받아쓰기를 시키는 경우에만 저작한다 (raise의 착지 (a)·(c)가 그 경우다).
- raise의 탐색 단계(착지 전)에서의 어떤 파일 쓰기.
- 노드 스키마의 임의 확장 (없는 필드 발명 금지 — 형식이 불확실하면 기존 노드 파일을 참조).

## 7. 완료 기준

- work(+구성품 2)·raise가 각각 단독 실행 가능하고, `/shall.work`가 정지 2회 외에 멈추지 않고 한 사이클을 완주한다.
- report가 만든 트리가 `shall check`를 통과한다 (red 0). Journal 최상단에 User Prompt 섹션이 verbatim으로 존재하고, WorkLog→task·TCR→task·Evidence→AC 엣지가 조립 규칙대로 걸려 있다.
- work.todo가 어떤 파일도 쓰지 않는다.
- 단독 work.report가 git 히스토리에서 트리를 재구성해 낸다 (Journal 부재 시 범위 질문 포함).
- raise가 착지 전까지 어떤 파일도 쓰지 않고, 네 착지 (a)~(d)가 각각 동작한다: (a) Decision+대상 수정, (b) WorkLog 연결 없는 단독 Finding (`shall check` 통과 — red 아님), (c) Decision—RESOLVES→Finding 동시 저작, (d) 등록 0으로 정상 종료.
- raise가 `$ARGUMENTS`로 발화를 받고, 빈 입력이면 절차 시작 전에 물음표를 먼저 묻는다.
- raise가 사이클을 시작하지 않는다.
- 단독 yellow Finding이 리뷰 큐에 "단독 발견"으로 노출된다.
- 스킬 본문에 노드 스키마 상세가 복제되어 있지 않다 (참조 지시만).
- 정지 1의 제안이 최대 3개 묶음이며, 3 초과는 사용자 명시 요구 + 권장 고지 후에만 발생한다.
- `/shall.work --dry`가 정지 없이 예보를 출력하고, 실행 전후 git status·spec/·ledger/가 완전 동일하다.
- `/shall.work --auto`가 터미널 질문 없이 report 기입까지 완주하고, 미완 항목마다 사유가 남는다.
